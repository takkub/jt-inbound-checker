# v4.4.7 J&T Inbound Checker review

## Verdict

**FAIL / changes requested.** The URL and manifest changes are internally consistent, but the result-detection and dialog-cleanup paths contain false-PASS and unintended-confirmation cases. These are blocking because a waybill can be reported as staged when it was not, and a pre-existing confirmation dialog can be accepted even though it did not result from the current scan.

## Findings (ordered by severity)

### High — A late success toast from the previous waybill can PASS the current waybill

References: `content.js:175-188`, `content.js:263-266`, `content.js:319-331`.

`dismissStaleToasts()` only snapshots toast **nodes already visible before the current click**. Any success toast from the previous request that arrives after that snapshot is a new node, so `isFreshToast()` returns true. The success branch then returns `{ status: 'pass' }` without checking the waybill or a corresponding changed row.

This regresses the prior safety rule in v4.4.6, which explicitly did not treat success toast as a standalone PASS because a previous request's toast can arrive while the next request is pending. The node-identity snapshot filters lingering toasts, but it cannot correlate late asynchronous toasts to the click that caused them.

Impact: the current waybill can be recorded as passed, skipped by retries, and omitted from failure history even if it never entered the Scan list.

Recommendation: keep a changed row containing the current waybill as the authoritative PASS. If the new site truly has a toast-only success flow, require a success payload/text that contains the exact current waybill or another request-specific correlation signal; freshness alone is insufficient.

### High — Generic dialog cleanup can confirm a pre-existing dialog, including an Upload All confirmation

References: `content.js:50-51`, `content.js:193-198`, `content.js:232-240`, `content.js:322-335`.

The pre-click snapshot correctly records existing dialogs in `dialogsBefore`, so an unchanged dialog is ignored as a result. However, after every result (including timeout), `dismissMessageBox()` independently chooses the first visible `.el-message-box`, `.ant-modal`, or `[role="dialog"]` and clicks any exact `ตกลง`, `OK`, `Confirm`, or `确定` button. It does not check whether that dialog was new/changed for the current scan.

Counterexample: if an Upload All confirmation dialog is already open when a scan runs, its `Confirm`/`OK` button is eligible for the unconditional cleanup click. Thus the exact-`OK` filter prevents direct selection of the page's `Upload All` button, but the complete flow does **not** prove that Upload All cannot be confirmed indirectly.

Impact: an unrelated or destructive page action can be confirmed without the user's intent.

Recommendation: return the specific newly appeared/changed result dialog from `waitForDomResult()` and only dismiss that node. Never dismiss a dialog present in `dialogsBefore`, and avoid the generic `[role="dialog"]` fallback unless it is anchored to the Waybill workflow.

### Medium — `exist` classifies “does not exist” as duplicate/PASS

References: `content.js:54-60`, `content.js:232-247`.

Duplicate detection is a substring search containing the keyword `exist`. Therefore `isDuplicate('Waybill does not exist')` returns true. Dialogs and warning toasts route duplicate text to PASS, so an invalid/not-found waybill can be treated as already scanned.

This keyword predates v4.4.7, but v4.4.7 expands its use to Ant and generic dialogs/warnings on the new site, so it is directly relevant to the new compatibility path.

Recommendation: match positive phrases such as `already exists`, `already scanned`, or the known Thai duplicate messages, and explicitly reject negative forms such as `does not exist`, `not exist`, and `ไม่พบ` before duplicate classification.

### Medium — The final OK-button fallback is document-wide, not scoped to the Waybill control

References: `content.js:152-170`.

The ancestor search is scoped for up to seven levels, but when it finds nothing it falls back to the first exact `OK` button anywhere in the document. The exact-text predicate proves this cannot directly select a button whose visible text is `Upload All`; it does not prove the chosen `OK` belongs to the Waybill form.

Impact: on a page with another visible exact-OK control, the extension can activate the wrong action.

Recommendation: remove the document-wide fallback. Anchor the button to the Waybill form item/control group, or fail safely when no locally scoped exact-OK button exists.

### Low — The new content-script prefix pattern injects beyond the accepted route

References: `manifest.json:10`, `manifest.json:24`, `popup.js:14-28`, `content.js:70-81`.

`https://home-site.jtexpress.co.th/mailPutIn*` is a valid Chrome match pattern, but it also matches path prefixes such as `/mailPutInfo`. Popup and content-script route guards correctly reject those paths, so scan automation does not run there; the content script and version badge can still be injected outside the intended route.

Chrome ignores the path portion of a `host_permissions` entry, so that permission grants the whole exact host regardless of the apparent `/mailPutIn*` path. This is documented behavior, not a functional regression. The `content_scripts.matches` path is enforced. See [Chrome match-pattern documentation](https://developer.chrome.com/docs/extensions/develop/concepts/match-patterns).

Recommendation: use exact route patterns where practical (for example separate exact/base and subpath patterns) and write host permission as `https://home-site.jtexpress.co.th/*` so its actual scope is explicit.

## Checks that passed

- `node --check` passed for `content.js`, `popup.js`, `background.js`, `interceptor.js`, and `offscreen.js`.
- `manifest.json` and `version.json` parse as JSON.
- `manifest.json` and `version.json` both report `4.4.7`.
- Declared background, popup, content-script, offscreen, and HTML-referenced resources exist.
- Twelve targeted URL cases passed: new base/query/subpath accepted; new prefix-confusion, HTTP, and lookalike URLs rejected; legacy exact/query/subpath hash routes accepted; legacy non-hash and wrong hash routes rejected.
- Legacy manifest matching remains broad enough for hash routing (`https://home.jtexpress.co.th/*`), while popup/content guards require `#/mailPutIn`.
- New content matching covers `https://home-site.jtexpress.co.th/mailPutIn`, query strings, and accepted subpaths.
- Exact button text checking (`/^OK$/i`) means the direct button search cannot select a visibly labelled `Upload All` button.
- Row snapshots detect both newly inserted rows and same-node text changes across Element, Ant, and generic table selectors.
- Error snapshots and dialog snapshots compare both node identity and text, which is an improvement over the prior single-node/single-boolean snapshots.

## Targeted counterexamples reproduced

- `isDuplicate('Waybill does not exist') === true`.
- A toast node that arrives after the stale snapshot is classified fresh, and the success-toast branch unconditionally settles PASS.
- Static inspection confirms the document-wide exact-OK fallback and generic dialog `Confirm`/`OK` click are present.

## Residual verification

After fixing the blocking cases, an authenticated smoke test is still required on both:

1. `https://home-site.jtexpress.co.th/mailPutIn` (new UI), covering successful staging, invalid waybill, duplicate, late/overlapping toast, inline error, Ant warning/error/success notifications, modal, row insertion/update, retry, and a deliberately pre-existing unrelated dialog.
2. `https://home.jtexpress.co.th/#/mailPutIn` (legacy Element UI), covering the same pass/fail/duplicate/timeout paths and confirming no Upload All action or confirmation occurs.

The release ZIP itself was not available as an uncommitted local artifact, so only source-manifest/update-manifest/resource integrity was checked; final packaging should additionally load the actual ZIP as an unpacked extension and verify its root contains the expected extension files.
